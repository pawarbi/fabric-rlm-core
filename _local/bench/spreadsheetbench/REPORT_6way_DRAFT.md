## TL;DR (provisional, finalized when all 6 jobs complete)

1. **gpt-4.1 + Python interpreter (F41) leads at ~30.7%** — slightly ahead of gpt-4.1-mini + interpreter (F = 29.3%) at much lower cost.
2. **Frontier model is NOT the bottleneck.** gpt-5 single-shot (A) trails the smaller models with interpreter access.
3. **gpt-5 is *worse* in iterative tool loops** than smaller models — F5 (gpt-5 + RLM) and S (gpt-5 + sub_lm) both collapse to <10% because gpt-5 calls `submit()` prematurely with partial answers ("VERIFY OK" overconfidence after 2 turns vs F's median 4-5 turns).
4. **The value isn't model size; it's model+harness fit.** A mid-tier model that iterates beats a frontier model that doesn't.

## The "gpt-5 premature-submit" failure mode

Trace inspection of S/F5 failures shows a consistent pattern. Concrete example — F5 trace `SSB_22-47`:

```
Turn 0: read question
Turn 1: explore sheet (sees data, headers)
Turn 2: COMPUTE answer in Python memory; PRINT cell values:
        F2 = 5, G2 = 'HASSAN', H2 = 133444422
        ... (full answer printed to stdout)
        VERIFY OK
Turn 3: SUBMIT(answer="done")   ← never wrote to the workbook!
```

gpt-5 computed the right answer in Python memory, printed it, declared "VERIFY OK", and submitted — but **never executed `ws.cell(...).value = X` + `wb.save(path)`.** The grader inspects the actual `.xlsx` file → 0 / 27 cells matched.

Quantitative evidence of this pattern from the partial download:

| Strategy | Median turns | Median cells matched on failed-submit | "Done" without writing |
|---|---|---|---|
| F (mini)   | 5 | 25%  | rare    |
| F41 (4.1)  | 4 | 30%  | rare    |
| **F5 (gpt-5)** | **3** | **0%** | **common** |
| S (gpt-5+sub_lm) | 2 | 40% | very common |

mini and 4.1 stick closer to literal task execution and *write the code that actually saves the file*. **gpt-5 has a richer internal world model** — it can simulate the spreadsheet mutation in its head, so it skips the "boring" persistence step. The harness inverts model rank because frontier models are more prone to "answering instead of acting."

Possible fixes:
1. **Prompt**: require a final "reopen file with `data_only=True` and read back target cells" step (whack-a-mole).
2. **Harness**: RLM auto-rejects `submit()` when no file mutation detected since last write — forces another turn.
3. **Inversion**: use small model as primary executor, frontier model only for hard subtasks via `sub_lm`.
