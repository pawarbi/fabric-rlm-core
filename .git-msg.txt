Withdraw F20; the arm design was already controlled

I filed F20 claiming arms B and C were data-starved, built corrected arms,
committed them, and spent a live run on it. The claim was wrong.

A knowledge package carries its own source bindings. runtime.py:1268 merges
them into the task inputs, so arms B and C reach the same data as arm A
through a different door, and the ValueError at runtime.py:1233 refusing a
duplicate alias is deliberate -- an alias must not carry two meanings in one
task. Arm B produced the correct value on 12 of 45 descriptive trials, which
is not something a starved arm can do.

The corrected arms failed 45 of 45 trials each with "task inputs conflict with
knowledge source aliases". A result that uniform is a bug report about the
harness, not a finding, and it was cheap to read that way immediately.

Reverted in full. test_arm_contract.py pins the binding contract so the same
misreading costs a test run rather than a live one. The register now carries
F20 as withdrawn, including how it happened, because the rule I broke was one
already written down: find the emitting line in fabric_rlm before filing.

What survives is the number F20 was obscuring. Arm B is incomplete on 51.1%
of trials against 15.6% for arm A, and since arm B reaches the data, that is
a real and more serious finding than the accuracy gap it hid behind.
