**The engine works.** Easy tier went from a complete shutout to a clean
sweep on a single ~15-line code change. Medium tier (deliberately
selected MCM hard cases from LongCoT pilot 20) improved 0 → 1 with the
adaptive ladder reaching the strong-LM rung. Hard tier reached the top
of the ladder on every case but cannot make GPT-5 solve a 400-int JSON
graph algorithm in one response — that's a model ceiling, not an engine
bug, and the engine correctly burns its full budget trying.

## 2 — The bug that was hiding behind everything (now fixed)

`fabric_rlm/prompts.py:_task_and_outputs` did not parse string
signatures (`'question -> answer'`). Strings have no `.output_fields`
attr, so the function returned `(task_description, [])`. That empty
list flowed through `_required_output_fields()` into
`validate_submit_payload(payload, ())` which short-circuits at line 1559
with `if not fields: return OK`. **Result: SUBMIT validation never fired
for string signatures.** The cheap LM happily called
`SUBMIT(output="391")` instead of `SUBMIT(answer="391")`, the engine
returned success with the wrong key, and tier validators (which look up
`payload['answer']`) saw empty strings everywhere.

This is why every tier was 0/N before the fix. It is also why the
adaptive ladder appeared to "not be doing anything" — it had nothing to
escalate against, because `validator(result)` was passing rubbish.

Fix (commit `4993145`):
- New `_parse_string_signature_outputs()` helper that parses
  `'inputs -> outputs'` and strips type hints (`answer: int` → `answer`).
- `_task_and_outputs` now dispatches on `isinstance(signature, str)`
  before the `inspect.getdoc` path.
- 78 lines of new tests covering string-sig output extraction and the
  adaptive runtime end-to-end with a string sig.

Easy tier 0/5 → 5/5 confirms the fix on the first re-run.

The ladder works exactly as designed — every case climbs to rung 4 and
fans out across two parallel strong-LM rollouts. The engine correctly
stops with `policy: stop_fail (ladder exhausted)` once the strong LM
rung is also exhausted. **The cases themselves are unsolvable by GPT-5
in single-shot reasoning** — they are 8-12 KB prompts asking for the
output of a graph algorithm that genuinely requires running the
algorithm. This is the right failure mode: the engine doesn't pretend
to succeed.

## 4 — What the trajectories say about the strategy

### Things the engine got right

1. **Validator-only trigger is the right default.** Every escalation
   in this run was driven by a real validator failure, not heuristics.
   None of the rung climbs were unjustified.
2. **`skip_more_turns_when_submitted=True` works as designed.** Rung 1
   (`max_turns ×2`) was correctly skipped on Medium and Hard cases
   where the cheap model already submitted a wrong-but-structured
   answer — there is no point re-running the same prompt twice if the
   model already made up its mind. The one case that DID try rung 1
   (VLIW) had a non-submitted rung 0, which is exactly when more turns
   helps.
3. **Best-of-N tie-break is deterministic.** Rung-3 produced two
   rollouts per attempt as configured (`parallel_rollouts=2`); winner
   selection is stable on retry.
4. **Strong-LM rung is reachable when you size the budget.** The first
   hard run had `max_attempts=5` and never reached rung 4 because
   parallel rollouts ate the budget; bumping to 6 fixed it. **0.1.11
   should default `parallel_rollouts × max_attempts ≥ 6` automatically**
   so users don't trip on this.

### Things the engine could do better (recommendations for 0.1.11)

1. **Per-template starting rung (Thompson-sampling bandit).** On the
   MFMC cases the cheap LM produced an 8-int answer where 400+ were
   expected. That is ~$0.02 wasted before the ladder even decides to
   escalate. A per-template bandit would learn after one or two MFMC
   failures that this template should start at rung 2 or 3, and skip
   rungs 0/1 entirely. Suggested implementation:
   - `BanditPolicy(LadderPolicy)` that maintains a `Beta(α,β)` prior per
     `(template, rung)` pair.
   - Thompson-sample the starting rung at attempt 0; from then on use
     the ladder.
   - Persist the priors to the lakehouse so they accumulate across
     notebook runs.
   - Estimated savings: ~30-40% of cheap-LM tokens on
     known-too-hard templates, with no loss of accuracy.
2. **Format-aware feedback injection.** The verifier
   (`verify_cs_response`) returns a `wrong_formatting` flag when the
   model failed to produce the required output shape (e.g. wrote
   `solution = [...]` instead of `solution = {"final_capacities":
   [...]}`). Adaptive should pipe this back into rung-1 feedback as
   `Reason: wrong output format. Expected JSON object with key
   "final_capacities".` The plumbing already exists
   (`render_feedback_block` in `adaptive_policy.py:599`) — what's
   missing is having `verify_cs_response`-style validators return a
   `ValidationVerdict(passed=False, feedback="...")` instead of a bare
   bool.
3. **Compute-optimal allocator (paper-style).** The plan already
   describes this as `Budget(compute_optimal=True)`. Skip rungs 0-1
   entirely when a difficulty estimator (e.g. prompt length > 8 KB +
   structured-output template) suggests rung 2+ is the floor. Keep
   the bandit as the empirical version and the difficulty estimator
   as the prior version of the same idea.
4. **Better stop signal at rung 4.** Right now the ladder runs rung 4
   with `parallel_rollouts=2` and discovers both rollouts fail
   independently. If two strong-LM rollouts disagree but neither
   passes, that's a structural-disagreement signal that the validator
   itself may be over-strict — at minimum the report should surface
   "both rollouts disagreed, second rollout's answer was X" so the
   user can hand-grade.
5. **Token instrumentation is broken end-to-end.**
   `total_prompt_tokens` and `total_completion_tokens` are always
   `None` in the trajectory metadata. `FabricLM` doesn't surface usage
   on its responses. Until this is fixed we cannot compute the NCU
   numbers the bench plan promised. **0.1.11 must fix this** —
   probably by patching `_aggregate_trajectory_metrics` to fall back
   to a per-call accumulator if the LM doesn't return usage.

## 5 — Engine bugs found and fixed this run

| # | Symptom | Root cause | Fix | Commit |
|---|---------|-----------|-----|--------|
| 1 | All tiers 0/N regardless of model | String signatures bypass SUBMIT validation | Parse `'inputs -> outputs'` form in `prompts.py` | `4993145` |
| 2 | Medium tier crashed with `'dict' object has no attribute 'lower'` | Notebook validator did `expected.lower()` on dict-typed expected answers | str-coerce expected before normalize, and prefer `verify_cs_response` for templated cases | (in `scripts/build_tier_notebooks.py`, committed with notebooks) |
| 3 | Hard tier never reached strong LM | `max_attempts=5` consumed by `0,1,2,3,3` (two rollouts at rung 3 count as two attempts) | Bumped hard-tier `max_attempts=6`. **0.1.11 should auto-size this in `LadderPolicy`.** | (notebook commit) |

## 6 — Bandit experiment status

Not implemented this run. Cost-benefit on a 4-case hard fixture wasn't
worth the risk of introducing a third moving part on top of the
engine fix and validator fix. Recommendation captured as item 1 in §4
above. The interface is fully designed
(`BanditPolicy(LadderPolicy)`, persistent priors), needs ~150 lines of
implementation + tests + a 20-case bench run to validate.
