# Phase 3 — Feature C ship decision (post duck-review)

> **Reading order**: §1 → §2 (the verdict & why it changed) → §6 (what
> we ship) → §9 (what's next).

## 1. TL;DR

We implemented Feature C (self-consistency cluster tiebreaker) per the
SRLM paper. **The implementation is correct and well-tested.** The live
A/B bench showed +17pp on DABench for `adaptive_c_minrung3`, but
post-bench duck review and a counterfactual replay analysis prove that
**this lift is sampling variance, not a causal effect of selector C** in
the current bench harness.

We are shipping Feature C **opt-in, default-OFF**, with documentation
that explicitly states the bench harness cannot demonstrate a causal
lift in this regime — and naming the regimes where it should help.

## 2. What changed since the first draft of this report

The first draft (now deleted) claimed:

- "Feature C adds +17pp accuracy on DABench"
- "Cluster size predicts correctness (7.2% → 34% → 82.8%)"
- "Composition with Feature A is broken / regresses"

Duck review (B1, B2, B3) flagged all three claims as confounded or
overstated. We did the work to validate, and the duck was right on every
point:

| Claim | Duck flag | Reality |
|---|---|---|
| +17pp causal lift | B1 (validator-as-grader) | Counterfactual replay flips **0/64** decisions when C key is applied to the SAME baseline candidate sets. The lift is candidate-sampling variance, not selection. |
| 7→34→83% calibration | B2 (Simpson's paradox) | Pooled monotonicity is an easy/math artifact. On DABench (the only signal-bearing domain) the trend is **flat or negative** across all configs (size-3+ = 0% pass). |
| A+C composition regression | B3 (`_best_partial` overwrite) | Observability rows for failed rollouts get rewritten by the exhausted-run selector, which doesn't forward `prefer_consensus`. The "regression" is a measurement artifact, not a real composition bug. |

## 3. The causal validity argument (made concrete)

The bench validator (`validate_question_passed`) is the selector's
**first** sort key AND the final grader. So:

```
candidate_set has ≥1 passing candidate  →  any selector picks a passing one  →  same final pass
candidate_set has 0 passing candidates  →  any selector picks a failing one  →  same final fail
```

Selector C can only differentiate **which** passing (or which failing)
candidate is picked, not whether the rollout passes overall. Therefore
the +17pp DABench number cannot be selector C's doing — it must come
from `adaptive_c_minrung3` happening to draw more passing candidates
than baseline (config-dependent prompts, rollout timing, thread
scheduling).

**Empirical confirmation** (`bench/adaptive/p3_counterfactual.md`,
generated by `_counterfactual_replay.py`):

| domain | rung3 cases | with cluster>1 | C winner-flips | C pass-flips |
|---|---:|---:|---:|---:|
| dabench | 24 | 8 | **0** | **0** |
| easy_calibration | 10 | 10 | 0 | 0 |
| math | 10 | 10 | 0 | 0 |
| longcot/ssb | 20 | 0 | 0 | 0 |
| **TOTAL** | **64** | **28** | **0** | **0** |

When applied to the same captured candidate sets, C key picks the same
candidate as baseline key in every rung-3 rollout we ran. Even where
clusters of size 2 or 3 exist, the existing tie-breakers (validator
verdict, score, confidence, payload completeness) already determine the
winner before cluster_size enters the comparison.

## 4. Where Feature C *should* help (paper's regime)

The SRLM paper (Alizadeh et al., arXiv:2603.15653) demonstrates lifts on
**long-context tasks where the validator is weak or absent**. There,
selector signals (consensus, trace length, verbalized confidence)
dominate because there's no programmatic ground-truth check to dominate
them. Two regimes where C is reasonably expected to help:

1. **User has no programmatic validator** (or it always returns
   `passed=True`). Then `passed`/`score`/`conf` are tied across
   candidates and `cluster_size` is the first real signal.
2. **User's validator is a weak proxy for the true grader** (e.g.,
   "JSON parses" vs "answer is correct"). Then multiple candidates pass
   the validator with different correctness; consensus may identify the
   correct one.

Our bench has neither property. Validating Feature C properly requires a
new bench in one of those regimes. **This is a Phase 4 task.**

## 5. Failure mode: degenerate-value amplification

Even where C does fire, it can amplify wrong answers when multiple
candidates produce the same degenerate sentinel:

```
DABENCH_0308 baseline candidate set:
  i=0  cluster_size=2  '@average_fare_mr[na], @average_fare_mrs[na], …'  ← wrong
  i=1  cluster_size=1  '@average_fare_mr[7.65], @average_fare_mrs[71.28], …'  ← correct
  i=2  cluster_size=2  '@average_fare_mr[na], @average_fare_mrs[na], …'  ← wrong (same as i=0)

baseline picks i=0 (-idx tiebreak).  C key would also pick i=0
(cluster_size=2 ties between i=0 and i=2; -idx breaks toward i=0).

If baseline had instead picked i=1 (the lone correct answer),
C would have actively flipped to the degenerate cluster.
```

We hardened the canonicalization against the most obvious sentinels:

- **Phase 3** (this PR): `_canonicalize_answer` now treats
  oversized integers, NaN, and ±Inf as **non-clusterable** (each gets
  its own singleton id rather than collapsing). New unit tests:
  `test_feat_c_canonicalize_handles_oversized_int`,
  `test_feat_c_canonicalize_treats_nonfinite_as_noncluster`. This also
  fixes a latent crash bug — `_compute_consensus_clusters` runs in
  observability mode even when the flag is OFF, so an unhandled
  `OverflowError` on a 200+ digit int could crash *default-config* runs.
- **Phase 4 backlog**: extend the sentinel list (string forms like
  `"file not found"`, `"data unavailable"`, `"n/a"`, all-zero tuples,
  empty results) by maintainer-extensible policy.

## 6. What we ship in Phase 3

**Code (already merged in commit `afd3d17`, plus this PR's hardening
patch):**

- `select_best_of_n(records, *, prefer_consensus=False, consensus_answer_keys=("answer",))`
  - Default `prefer_consensus=False` → byte-identical to legacy call.
  - With `prefer_consensus=True` → cluster_size is inserted into the
    sort key just before the `-rollout_index` deterministic tiebreaker.
- Always-on observability: every selection writes
  `consensus_cluster_id`, `consensus_cluster_size`, and
  `candidate_answer_preview` to `record.metadata["srlm"]` regardless of
  flag, so post-hoc analysis of legacy runs is possible.
- `_canonicalize_answer` hardened against degenerate numeric sentinels
  (NaN, ±Inf, oversized ints).
- 19 Feature C unit tests passing.
- 145 targeted tests across `adaptive_policy`, `adaptive_runner`,
  `srlm_eval_harness` passing.

- `bench/adaptive/p3_counterfactual.md` — replay analysis.
- `bench/adaptive/p3_trajectory_analysis.md` — full trajectory cuts
  with stratified consensus calibration.
- Module docstring on Feature C cites this file for "when to enable".

## 8. Composition gap (`adaptive_all_minrung3`)

The previous report noted that `adaptive_all` was wired with
`prefer_shorter_traces=True + prefer_consensus=True` but **without**
`min_rung=3`, so only 4/64 of its rollouts reached rung-3 — invalidating
the +1.5pp composition number. We did NOT re-bench `adaptive_all_minrung3`
because:

1. The counterfactual replay shows C alone flips 0 decisions on this
   bench. A+C cannot do better than A on the same candidate sets when C
   contributes nothing.
2. A live re-bench would still suffer the validator-as-grader confound,
   so any composition number it produced would be sampling noise.
3. Spending another ~$0.50 of API budget on a measurement we know is
   structurally uninformative isn't the right use of the budget.

The right next step on composition is the Phase 4 long-context bench.

## 9. Phase 4 backlog (priority order)

1. **Implement Feature B (verbalized confidence)** — the only signal
   from the SRLM paper we don't have yet. Same opt-in pattern.
2. **Long-context bench harness** — the regime where SRLM signals are
   actually expected to help. Requires either (a) a benchmark whose
   validator differs from its grader, or (b) tasks with no validator at
   all (LLM-as-judge final eval).
3. **Counterfactual evaluator generalization** — productize
   `_counterfactual_replay.py` into a CLI that accepts arbitrary
   selector-key constructors. The pattern (replay alternative selectors
   against captured candidate sets) is the cheapest way to validate
   any new BoN ranking rule.
4. **Sentinel-detection extension** — extend `_canonicalize_answer` to
   treat string sentinels (`"file not found"`, `"n/a"`, `"data unavailable"`,
   all-zero tuples) as non-clusterable. Maintainer-extensible policy.
5. **Fix `_best_partial` measurement loss** — capture the C-aware
   selector key in observability BEFORE the exhausted-run overwrite, so
   post-hoc analysis of failed rollouts is honest.
6. **Early-exit policy** (Feature E) — trajectory analysis showed ~80%
   of rung-3 spend buys no decision (all 5 candidates pass OR all 5
   fail). Skipping rung-3 in those cases is a cost-saving novel
   contribution candidate.
7. **Fix longcot / SSB graders** — current substring stubs grade 0%
   across all configs; we have no signal from these domains.

## 10. What I learned (and would do differently)

- **Build the counterfactual replay before running the live A/B.** It's
  an offline, free, deterministic test of whether a selector change can
  even be expected to flip the bench. Running expensive live A/Bs to
  measure noise was a waste of the budget — but the replay needed the
  observability schema to land first, so this was a chicken-and-egg.
- **Stratified analysis from day 1.** Pooled trajectory cuts hide
  Simpson's paradox in any benchmark with mixed-difficulty domains.
- **Validator-as-grader is a fundamentally weak setup for testing
  selectors.** Any future selector work needs a bench where validator
  and grader diverge.
